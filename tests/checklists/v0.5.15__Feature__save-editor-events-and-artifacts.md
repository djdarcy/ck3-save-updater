# Human Test Checklist: the save editor's events and artifacts

**Target version:** 0.5.15 (built across 0.5.12 to 0.5.15)
**Ships with commit:** v0.5.15: artifacts and give-artifact
**Companion automated tests:** 43 tests in `tests/test_edit_events.py` (25), `tests/test_edit_artifacts.py` (6) and `tests/test_edit_reshape.py` (12). Whole suite: 1379 passed, 7 skipped.

## What this is

A hand-run companion to the tests of the event and artifact edits. It follows `v0.5.10__Feature__save-editor-set-sex-and-the-front-door.md`, which covers the editor's front door, the ledger, revert and backups. Here a person checks what the tests cannot: how the lists read on a real save, and what the game shows after an edit.

Codes used here:

| Code | Meaning |
|---|---|
| HV.n | a High-Value Verification step, the five-minute pass |
| MANUAL | a step only a person can do (the game, a judgement by eye) |

## Prerequisites

1. `ck3update --version` prints 0.5.15 or later.
2. A real text save (not ironman). **Work on a copy, in a scratch folder. Never run these steps on a save you play.**
3. The game installed, so `event-schedule` can check an event's name. (`ck3update status <copy>` names the game folder it finds.)
4. To load an edited copy in the game, put it in the game's save folder under a name that marks it as a test.

Set up the scratch folder and the copy (pick your shell):

**cmd.exe**:
```cmd
mkdir %TEMP%\ck3events
copy "C:\path\to\My_Campaign.ck3" %TEMP%\ck3events\Camp.ck3
cd /d %TEMP%\ck3events
```

**PowerShell**:
```powershell
New-Item -ItemType Directory -Force "$env:TEMP\ck3events" | Out-Null
Copy-Item "C:\path\to\My_Campaign.ck3" "$env:TEMP\ck3events\Camp.ck3"
Set-Location "$env:TEMP\ck3events"
```

**POSIX**:
```bash
mkdir -p /tmp/ck3events && cp "/path/to/My_Campaign.ck3" /tmp/ck3events/Camp.ck3 && cd /tmp/ck3events
```

**Reset between sections:** delete every file in the scratch folder except `Camp.ck3`.

## High-Value Verification (~5 minutes, plus the game for HV.4 and HV.5)

### HV.1 The lists read well on a real save

Validates: a player can find an event's number and an artifact's id.

- [ ] **Steps** (same in every shell; use a child for the first and a ruler for the second):
  ```
  ck3update edit Camp.ck3 events "<a child's name>"
  ck3update edit Camp.ck3 artifacts "<a ruler's name>"
  ```
- [ ] **Expected:** a first line naming the character, then one line per event (number, date, name, seed, role) soonest first, or one per artifact (id, type, name), then a count. No new file in the folder.
- [ ] **Check by eye:** are the columns aligned? Is a long event name still readable?
- [ ] **Why this matters:** every other step needs a number taken from these lists.

### HV.2 A reroll changes only the seed

Validates: the edit a player will use most.

- [ ] **Steps:**
  ```
  ck3update edit Camp.ck3 event-show <number>
  ck3update edit Camp.ck3 event-reroll <number> --yes
  ck3update edit Camp__event-reroll.ck3 event-show <number>
  ```
- [ ] **Expected:** the two blocks are the same except for the `seed=` line.
- [ ] **Why this matters:** a reroll that touched anything else would change the campaign in ways the player did not ask for.

### HV.3 A removal shifts the numbers, and says so in the help

Validates: the one trap of numbering events by their order.

- [ ] **Steps:** list a character's events, `event-remove` the first of two, then list again in the output file.
- [ ] **Expected:** one event fewer; the later one's number is one lower. `ck3update help event-remove` says the numbers belong to one file.
- [ ] **Why this matters:** a second removal with a stale number would take out the wrong event.

### HV.4 A scheduled event fires in the game (MANUAL)

Validates: the event edits against the game itself.

- [ ] **Steps:**
  1. Pick a child with no sexuality yet and no queued events (`events <child>` says "no queued events").
  2. `ck3update edit Camp.ck3 event-schedule <child> child_personality.4015 <a date a week after the save's>`
  3. Load the output in the game and let two weeks pass.
- [ ] **Expected:** the event fires for that child. Note what you see: a notification, an event window, a change on the character.
- [ ] **Why this matters:** the tool was tested by comparing saves; nobody has yet watched a scheduled event arrive on screen.

### HV.5 A copied artifact in the game (MANUAL)

Validates: what the game shows for a copy.

- [ ] **Steps:**
  1. `ck3update edit Camp.ck3 give-artifact <a character who holds artifacts> <id of someone else's artifact> --yes`
  2. Load the output in the game and open that character's inventory.
- [ ] **Expected:** the copy is there, with the original's name and bonuses. The original is still with its owner.
- [ ] **Check by eye:** can the copy be equipped or put on display? Does its description, which names the original's history, read sensibly for the new owner? Does the game treat two artifacts of one name oddly anywhere?
- [ ] **Why this matters:** the game kept the copy in a save-to-save test; whether it is usable in play is unseen.

## Section 1: events

### 1.1 Refusals

- [ ] `event-show 0` and a number above the count: "this save has N queued events, numbered from 1".
- [ ] `event-schedule <child> not.an.event.name 990.1.1`: "an event is named namespace.number".
- [ ] `event-schedule <child> child_personality.999999 990.1.1`: "no event ... in the game's events".
- [ ] `event-schedule <child> child_personality.4015 <a date before the save's>`: refused, naming the save's date.
- [ ] Nothing is written by any of them.

### 1.2 An event of a mod

- [ ] **Steps:** schedule an event that only a Workshop mod of the save defines.
- [ ] **Expected:** accepted when the mod is installed. For a mod kept elsewhere (a local mod), refused; `--dangerous` schedules it, and the ledger entry says `"dangerous": true`.

### 1.3 The same schedule twice

- [ ] **Steps:** run the same `event-schedule` twice from `Camp.ck3` (`--force` the second time) and compare the two outputs with the hash command of the first checklist (HV.4 there).
- [ ] **Expected:** the same hash: the seed is fixed by the campaign, the character, the event and the date.

### 1.4 A removed event comes back by the game's rules (MANUAL, optional)

- [ ] **Steps:** remove a child's queued personality event, load the output, let a year pass, save, and list the child's events in that save.
- [ ] **Expected:** the removed event did not fire. The game may have queued a new one of its own.

## Section 2: artifacts

### 2.1 Refusals

- [ ] `give-artifact <character> 999999999`: "the save has no artifact".
- [ ] `give-artifact <a character who holds none> <id>`: "has no inventory in this save".
- [ ] Nothing is written by either.

### 2.2 The copy's id and the ledger

- [ ] **Steps:** after a `give-artifact`, run `artifacts` for the receiver in the output, and `python -m json.tool <output name>.edits.json`.
- [ ] **Expected:** the copy is listed last, under a new id (for a save with 4,702 artifacts, 4702); the ledger entry has two changes.

### 2.3 Revert

- [ ] **Steps:** `ck3update edit <output> revert --yes`, then `artifacts` for the receiver in the revert's output.
- [ ] **Expected:** the copy is gone; the list is as before.

## Section 3: your own view (optional)

- [ ] **Steps:** in a pack of your own, write the `who-is` view from `docs/writing-a-patch.md` ("A view"), `ck3update trust <pack>`, then `ck3update edit Camp.ck3 who-is <character>`.
- [ ] **Expected:** the view's lines; no new file. `ck3update edit --list` shows it as `ready`. Before `trust`, it is `not trusted` and refused.

## What the automated tests DO cover

| Area | Test file | Count |
|---|---|---|
| Reading queued events; the two views; remove; reroll; schedule and its refusals | `tests/test_edit_events.py` | 25 |
| Reading artifacts; the view; the copy, its id, its owner; refusals; revert | `tests/test_edit_artifacts.py` | 6 |
| The context an edit receives; views; one loader; three fixed defects | `tests/test_edit_reshape.py` | 12 |

Each of these tests was shown to fail when the behaviour it checks is removed (120 deliberate breakages across the editor, all caught).

Three game runs stand behind the edits, each on a copy of a real campaign with its prediction written first: a reseeded event rolled differently; a removed event did not fire and a scheduled one did; a copied artifact given to another character was kept.

## What the automated tests DON'T cover

- **What the player sees in the game.** The game runs compared saves. Nobody watched an event window open or an artifact appear in an inventory screen (HV.4, HV.5).
- **Events that need more than a character.** A scheduled event is given its subject only. An event that expects a second character or a title may misbehave; none was tried.
- **A real save's size and names.** The tests use saves of a few kilobytes. On a 240 MB save the lists take 9 to 15 seconds, and names appear as the save spells them.
- **Mods' events.** The lookup was tested with a made-up mod folder, not a real Workshop mod.
- **An artifact for a character who holds none**, and a new artifact made from nothing: the tool refuses the first and has no command for the second.

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command and its output.
3. Keep the ledger file and the output save (not your original).
4. File an issue naming this checklist and the version from `ck3update --version`.

## Cleanup

Delete the scratch folder, and the test copies you placed in the game's save folder.

**cmd.exe**: `cd /d %TEMP% && rmdir /s /q %TEMP%\ck3events`
**PowerShell**: `Set-Location $env:TEMP; Remove-Item -Recurse "$env:TEMP\ck3events"`
**POSIX**: `cd /tmp && rm -r /tmp/ck3events`
