## What this is

The release gate for the first version strangers install from PyPI: a person on a Windows machine follows the README from `pip install` to an updated save, on copies, and checks what only a person can judge: that it installs cleanly, reads clearly, finds the game and saves by itself, says what it will do before doing it, and never touches anything it was not asked to. A tester agent runs the scriptable parts first (see "Sweep" at the end); a person runs the rest.

## Prerequisites

1. Windows 10/11, Crusader Kings III 1.20.x installed through Steam, Python 3.10 or newer, at least 2 GB free in the temp folder.
2. **A scratch folder with copies, and a scratch settings file.** Never your real saves; never your real `config.toml`:

   **cmd.exe**
   ```cmd
   mkdir %TEMP%\ck3-040
   copy "<an old save>.ck3" %TEMP%\ck3-040\Old.ck3
   set CK3SM_CONFIG=%TEMP%\ck3-040\config.toml
   set CK3UPDATE_CACHE_DIR=%TEMP%\ck3-040\cache
   cd /d %TEMP%\ck3-040
   ```
   **PowerShell**
   ```powershell
   New-Item -ItemType Directory -Force "$env:TEMP\ck3-040" | Out-Null
   Copy-Item "<an old save>.ck3" "$env:TEMP\ck3-040\Old.ck3"
   $env:CK3SM_CONFIG = "$env:TEMP\ck3-040\config.toml"
   $env:CK3UPDATE_CACHE_DIR = "$env:TEMP\ck3-040\cache"
   Set-Location "$env:TEMP\ck3-040"
   ```
   **POSIX**
   ```bash
   mkdir -p /tmp/ck3-040 && cp "<an old save>.ck3" /tmp/ck3-040/Old.ck3
   export CK3SM_CONFIG=/tmp/ck3-040/config.toml CK3UPDATE_CACHE_DIR=/tmp/ck3-040/cache
   cd /tmp/ck3-040
   ```
3. A reference save for the old save's date (`docs/reference-save.md`), copied into the scratch folder as `Ref.ck3`.
4. **The game is never launched by this checklist.** Loading an output in the game is a separate, optional step at the end, on a copy.
5. **Reset between sections:** delete the scratch `config.toml` and the outputs (`del *__updated__*.ck3 *.report.json *.lint.json` / `Remove-Item *__updated__*` / `rm -f *__updated__*`).

## High-Value Verification (~10 minutes)

### HV.1: it installs and runs from PyPI
- [ ] **Steps:** in a fresh virtual environment, `pip install ck3-save-updater`, then `ck3update --version`.
- [ ] **Expected:** prints `ck3-save-updater 0.4.0`. If `ck3update` is "not recognized", `python -m ck3_save_migrator setup` says where pip put it and offers to fix PATH.
- [ ] **Why this matters:** the first command a stranger types.

### HV.2: `status` with no save finds the game and the saves
- [ ] **Steps:** `ck3update status`
- [ ] **Expected:** a GAME block (version, path, how it was found) and a SAVES block (your save folder, a count), no error, nothing written.
- [ ] **Why this matters:** discovery on someone else's machine is the tool's first promise.

### HV.3: `status` on an old save says what it will do
- [ ] **Steps:** `ck3update status Old.ck3 --reference Ref.ck3`
- [ ] **Expected:** a verdict first (READY ... with a time); blocks SAVE, GAME, RECORD, GAP, REFERENCE, PACKS, PATCHES, DETECTORS, OUTPUT, NOTES; while it works, a spinner names the step ("checking R11 ... (n of m)"); under two minutes on a large save; nothing written beside the save (a cached index may appear in the cache folder: the DETECTORS block says so).
- [ ] **Why this matters:** the plan is what makes the tool explainable.

### HV.4: `update` writes a new file and leaves the save alone
- [ ] **Steps:** `ck3update update Old.ck3 --reference Ref.ck3`
- [ ] **Expected:** `Old__updated__<game version>.ck3` plus its `.report.json` and `.lint.json` beside the save; `Old.ck3`'s bytes unchanged (compare its sha256 before and after: `certutil -hashfile Old.ck3 SHA256` / `Get-FileHash Old.ck3` / `sha256sum Old.ck3`); exit code 0.
- [ ] **Why this matters:** "never changes the save you give it" is the README's first promise.

### HV.5: a refusal says why and how to fix it
- [ ] **Steps:** copy `Ref.ck3` to `Ref2.ck3` in the save folder the tool searches (or the scratch folder, if it is the save folder), run `ck3update status Old.ck3` without `--reference`.
- [ ] **Expected:** `REFUSED` first, in about a second (no full read: "fail early"), the candidates listed, and `fix: pick one with --reference "<one of these>"`.
- [ ] **Why this matters:** a stranger's most likely first outcome is a refusal; it must be actionable.

## Section 1: install and setup
- [ ] **1.1** `pip install ck3-save-updater` on Python 3.10, 3.11, 3.12 and 3.13 where available: installs; `ck3update -h` opens with "start here" (status, then status on a save, then update) and lists every command once, under headings (updating a save, when something looks wrong, your own packs, setup, advanced); nothing in it is wider than 79 columns.
- [ ] **1.1a** `ck3update` with nothing after it prints the "start here" lines and `ck3update -h lists every command.`, exit 0 (no error). Would a first-time player know what to type next?
- [ ] **1.2** `ck3update -V` prints the same as `ck3update --version`; the old command name `ck3-save-migrator --version` still works (one-release alias).
- [ ] **1.3** `ck3update setup --dry-run` changes nothing in PATH or the registry and says what it would do.
- [ ] **1.4** PyPI's project page shows the licence as GPL-3.0-or-later and the README renders with its badges.

## Section 2: the plan (`status`)
- [ ] **2.1** On a 1.8-era save: the GAP block names the version span; PACKS names the built-in pack and why it is selected.
- [ ] **2.2** A save from before the 1.13 map rework: NOTES says it loads only with the transplant and how to ask for it.
- [ ] **2.3** `--plain` and `NO_COLOR=1` give the same plain text (no colour, no spinner); piped output (`> out.txt`) holds no escape codes.
- [ ] **2.4** In a console about 60 columns wide, nothing wraps back under a header; above 120 columns, lines stop at 120.
- [ ] **2.5** `[display]` in the scratch config (`align = "global"`, then `"blocks"`, `spacing = "blank"`): the layout changes as `docs/config.md` shows.
- [ ] **2.6** A save one hotfix behind the game: ALREADY CURRENT, "on the game's version line".

## Section 3: `update`
- [ ] **3.0** A mistyped `--old-game-dir` (a folder that does not exist, or one that is not a game's `game` folder): REFUSED at once, `fix: give the 'game' folder of the game version the save was made with`, nothing written. (The sweep of 2026-11-03 passed this path through bash unquoted, the backslashes were dropped, and before 0.3.24 the update ran on with a map of no titles.)
- [ ] **3.1** `update --dry-run`: the plan with counts; nothing written.
- [ ] **3.2** `update --in-place` on a copy: the copy is replaced, `<name>.bak.ck3` holds the original's bytes; running it again refuses to overwrite the `.bak` without `--force`.
- [ ] **3.3** A second save of the same campaign: RECORD shows the first update and `pre-filled:` rows for its inputs; nothing retyped.
- [ ] **3.4** `status` on the updated output: ALREADY CURRENT (or the re-check's "needed" lines with their `--rules` hint); `update` on it writes nothing without `--rules`.
- [ ] **3.5** Twice in a row on the same unchanged save: the second `status` says it read the block index from the cache; `ck3update cache where` names the folder and size; `ck3update cache clear` empties it; `[cache] index = false` stops it writing.

## Section 4: your own packs
- [ ] **4.1** After the first run, the packs folder (`%APPDATA%\ck3-save-migrator\packs`, or beside `CK3SM_CONFIG`) holds a README and `_example-pack`; `ck3update packs` lists what it found.
- [ ] **4.2** Copy `_example-pack` to `my-pack` (no underscore): `status` lists it and its patch; the patch writes only keys the game defines.
- [ ] **4.3** A pack that runs code is listed as not trusted and never runs until `ck3update trust <id>`; changing one of its files makes it untrusted again.
- [ ] **4.4** `ck3update help R11` explains a rule; `ck3update help <your patch id>` explains yours; an id no pack holds says so.

## Section 5: the other commands
- [ ] **5.1** `ck3update check Old.ck3`: each rule needed, done, or unknown (with why), nothing written.
- [ ] **5.2** `ck3update lint <the output>`: 0 errors on a good output; the families the game converts on load reported as info.
- [ ] **5.3** `ck3update gamediff <old game folder> <new game folder>` (if you have two): lists what changed.

## Section 6: the README as a stranger
- [ ] **6.1** Read README.md top to bottom on a machine where the game is in a non-default Steam library; every step works as written; every link opens; every glossary link lands on its entry.

## Optional: in the game
- [ ] **7.1** Copy the output into your save folder as `MIGRATE_TEST__040_<name>.ck3`, load it in 1.20, and save once. It loads; `error.log` holds no "Unexpected token" for a key the tool wrote.

## What the automated tests DON'T cover

- A clean `pip install` from PyPI on a machine that never had the source
- Steam discovery on another machine's library layout
- The spinner and colour in a real console (Windows Terminal, conhost)
- Whether the README reads well to someone new
- The game loading an output (never automated)
- Performance feel on a slower disk

## Reporting issues found

Note the section and step, the exact command and output (use `--plain`), the machine (Windows version, console, Python version); file an issue citing this checklist and the version.

## Cleanup

**cmd.exe**: `set CK3SM_CONFIG=` and `set CK3UPDATE_CACHE_DIR=`, then remove `%TEMP%\ck3-040`. **PowerShell**: `Remove-Item Env:\CK3SM_CONFIG, Env:\CK3UPDATE_CACHE_DIR`, then remove `$env:TEMP\ck3-040`. **POSIX**: `unset CK3SM_CONFIG CK3UPDATE_CACHE_DIR; rm -rf /tmp/ck3-040`. Your real saves and settings were never touched.

## Sweep

Before a person runs this, a tester agent runs Sections 2-5 against a temp config and scratch copies (never the real save folder's saves, never the game), and records results under `tests/checklists/results/`.
