# Human Test Checklist: a faster update, with the section index kept through edits

**Target version:** 0.4.31
**Ships with commit:** TBD (v0.4.31)
**Companion automated tests:** 12 in `tests/test_top_index_shift.py` and 3 in `tests/test_step_findings.py`. The full suite count is in the commit message.

## What this is

What a person runs to check 0.4.31 for themselves. It is a speed change with no change of behaviour.

An update edits the save many times, about 30 on a large save. After each edit the tool used to find every top-level section of the save again, a walk of about 6 seconds on a 220 MB save. It now moves the section positions it already knows by the size of each edit. The lint's own section finder uses the same positions. A third piece, letting a rule reuse its check's work, is in place but not switched on yet.

The output must be the same save, byte for byte. Measured on three saves of one campaign: the same output with the change on and off, and 17-31% faster (767 s -> 530 s on the largest).

## Prerequisites

1. Python 3.10 or newer.
2. A copy of an old save (1.8 or later). Name it `MIGRATE_TEST__speed.ck3`. **Never use your only save.**
3. Two environments, so the old and new versions can run side by side: a venv with the previous release (`pip install ck3-save-updater==0.4.29`, the latest on PyPI) and this checkout (`pip install -e .`).
4. **A cold cache for fair timing.** The tool keeps a speed-up cache between runs. Point each timed run at its own empty folder:
   - cmd.exe: `set CK3UPDATE_CACHE_DIR=%TEMP%\ck3cache_old` (then `_new`)
   - PowerShell: `$env:CK3UPDATE_CACHE_DIR = "$env:TEMP\ck3cache_old"`
   - POSIX: `export CK3UPDATE_CACHE_DIR=/tmp/ck3cache_old`

Run the commands from your save folder:
- cmd.exe: `%USERPROFILE%\Documents\Paradox Interactive\Crusader Kings III\save games`
- PowerShell: `"$env:USERPROFILE\Documents\Paradox Interactive\Crusader Kings III\save games"`
- POSIX (Linux): `~/.local/share/Paradox Interactive/Crusader Kings III/save games`

**Reset between runs:** delete the output the run wrote, and nothing else.
- cmd.exe: `del MIGRATE_TEST__speed__*`
- PowerShell: `Remove-Item MIGRATE_TEST__speed__*`
- POSIX: `rm -f MIGRATE_TEST__speed__*`

## High-Value Verification (~15-30 minutes, mostly waiting)

### HV.1 -- the same save comes out, faster

- [ ] **Steps:** with the old version, then the new one, each with its own empty cache folder (Prerequisites 4):
  1. `ck3update update MIGRATE_TEST__speed.ck3 --no-ask -o MIGRATE_TEST__speed__old.ck3`, and time it.
  2. `ck3update update MIGRATE_TEST__speed.ck3 --no-ask -o MIGRATE_TEST__speed__new.ck3`, and time it.
- [ ] **Expected:** the "gamestate sha" line is the same in both. The new run is faster. On a large save expect minutes, not seconds; on a small one the gain is small.
- [ ] **Why this matters:** the change is only allowed to make it faster. Any difference in that line is a bug.

Timing, if you want numbers:
- PowerShell: `Measure-Command { ck3update update ... }`
- POSIX: `time ck3update update ...`
- cmd.exe: note `%TIME%` before and after.

### HV.2 -- the self-check finds nothing wrong

- [ ] **Steps:** turn the self-check on, run the new version, then turn it off:
  - cmd.exe: `set CK3UPDATE_CHECK_INDEX=1`, then the HV.1 step 2 command, then `set CK3UPDATE_CHECK_INDEX=`
  - PowerShell: `$env:CK3UPDATE_CHECK_INDEX = "1"`, the command, then `Remove-Item Env:\CK3UPDATE_CHECK_INDEX`
  - POSIX: `export CK3UPDATE_CHECK_INDEX=1`, the command, then `unset CK3UPDATE_CHECK_INDEX`
- [ ] **Expected:** no "the shifted top-level index differs from a fresh walk" error. The same "gamestate sha" as HV.1. It is slower than HV.1's new run, because it checks every step the slow way too.
- [ ] **Why this matters:** this mode compares every shortcut with the full walk on your own save. A pass here means the shortcut was right on every edit.

### HV.3 -- the lint says the same

- [ ] **Steps:** `ck3update lint MIGRATE_TEST__speed__old.ck3`, then the same with `__new`.
- [ ] **Expected:** the same findings and counts.
- [ ] **Why this matters:** the lint now finds sections through the shared positions.

### HV.4 -- status is unchanged

- [ ] **Steps:** `ck3update status MIGRATE_TEST__speed.ck3` with each version.
- [ ] **Expected:** the same verdict and the same PATCHES and DETECTORS blocks (times aside).

## What the automated tests DO cover

| Area | Test file | Count |
|---|---|---|
| the positions moved through random edit passes equal a fresh walk; deletions; an insert just before a closing brace; braces inside quoted text | `tests/test_top_index_shift.py` | 5 |
| edits the shortcut must not take (between sections; text that would close a section) fall back to the walk; nothing is built early; the self-check both ways | `tests/test_top_index_shift.py` | 4 |
| the lint's section finder takes the shared positions, gives the same result, and still handles an unclosed section | `tests/test_top_index_shift.py` | 3 |
| a rule reuses its check's work only for the very same bytes and inputs (not switched on yet) | `tests/test_step_findings.py` | 3 |

Each was shown to fail when the behaviour it guards was broken on purpose: 13 deliberate breakages, all caught.

## What the automated tests DON'T cover

- The real timing and memory on a 220 MB save, and how much faster it feels.
- The mix of edits a real campaign produces: the tests use small synthetic saves.
- Saves from other game versions and campaigns than the three it was measured on.

## Reporting issues found

1. Note the HV number and the shell.
2. Keep both outputs and the two "gamestate sha" lines.
3. File an issue on GitHub referencing this checklist and version 0.4.31.

## Cleanup

- Delete `MIGRATE_TEST__speed.ck3` and its `__old`/`__new` outputs and reports (Reset above).
- Delete the cache folders you made (`ck3cache_old`, `ck3cache_new`).
- Unset `CK3UPDATE_CACHE_DIR` and `CK3UPDATE_CHECK_INDEX` (or close the shell).
