# Human Test Checklist: lint -- what the current game will still reject

**Target version:** 0.3.0
**Ships with commit:** `v0.3.0: lint reports what the current game will reject before you load the save` (TBD until committed)
**Companion automated tests:** 210 passed, 3 skipped (the skipped three are opt-in real-save tests, enabled with `CK3_REAL_SAVES=1`). New in this version: `tests/test_lint.py` (53 tests: structure and cross-reference checks, the key-name check, the reject families, the CLI wiring, discovery off by default). Unchanged: `tests/test_savefile.py`, `tests/test_gamestate.py`, `tests/test_rules.py`, `tests/test_religion.py`.

## What this is

Version 0.3.0 adds `ck3-save-migrator lint <save>` and runs the same checks by default at the end of `migrate`. Lint reads a save in the current game's layout and reports, in four severities, what is wrong with it or what the game will complain about when it loads: **error** (the migrator's own post-conditions failed; exit code 4; the output is still written so it can be inspected), **warn** (links to characters or titles the save does not contain, and similar), **reject** (lines the current game's `error.log` will contain, family by family, with a predicted count and examples), and **info** (key names unknown to the reference save, the game and the mods). The findings go to stdout, to `<output>.lint.json` beside each migrated output, and into the `--report` file. This checklist is for a person with the game installed and a real old save: the automated tests prove the checks fire on synthetic fixtures and that the counts match two archived logs, but only a person can judge whether the report is readable, whether the counts match *their* game's log, and whether the exit codes and files land where a user expects.

## Prerequisites

1. Windows, macOS or Linux with Python 3.10+ and this repository checked out; `pip install -e ".[dev]"` done (or the wheel installed; the commands below work either way).
2. An old save (written by game version 1.8 or 1.9) **and** a reference save written by the installed game version, at the same start date as the campaign if possible. If you have no old save, Section 1 still runs on the synthetic fixture.
3. The current game installed (lint finds Steam's usual folders; otherwise pass `--game-dir <game>/game`). Without it, Section 3's families are skipped with a message, which is itself a step (3.4).
4. **Isolation:** work in a scratch folder; never point lint or migrate at the game's own `save games` folder. Copy your old save into the scratch folder first. Nothing in this checklist writes to the game's folders.
5. Reset between sections: delete the scratch folder's `*.migrated.ck3`, `*.lint.json` and `*.json` report files.

Set the scratch folder and the two environment variables the tests use (pick your shell):

**cmd.exe**:
```cmd
set CK3_SCRATCH=%TEMP%\ck3-lint-check
mkdir %CK3_SCRATCH%
copy "<your old save>.ck3" %CK3_SCRATCH%\old.ck3
set CK3_REFERENCE_SAVE=<path to your reference save>.ck3
```

**PowerShell**:
```powershell
$env:CK3_SCRATCH = "$env:TEMP\ck3-lint-check"
New-Item -ItemType Directory -Force $env:CK3_SCRATCH | Out-Null
Copy-Item "<your old save>.ck3" "$env:CK3_SCRATCH\old.ck3"
$env:CK3_REFERENCE_SAVE = "<path to your reference save>.ck3"
```

**POSIX**:
```bash
export CK3_SCRATCH=/tmp/ck3-lint-check
mkdir -p "$CK3_SCRATCH"
cp "<your old save>.ck3" "$CK3_SCRATCH/old.ck3"
export CK3_REFERENCE_SAVE=<path to your reference save>.ck3
```

The synthetic fixture (for Section 1 without a real save) is built by a Python call, not a script (the module has no command line):

```
python -c "import sys; sys.path.insert(0, 'tests/fixtures'); from make_ck3 import build_ck3; open(sys.argv[1], 'wb').write(build_ck3())" <scratch>/fixture.ck3
```

The fixture is a save in the *old* layout, so lint reports only its structure findings on it; the severities and families appear on a migrated output (HV.1 onward).

Unzipping a migrated output to read the gamestate (used in 4.1): the `.ck3` file is a text header followed by a zip; `ck3-save-migrator inspect <file>` prints the header and the zip members, and the Phase 1 checklist (Section 1) shows the Python two-liner that extracts `gamestate`.

## High-Value Verification (~5 minutes, ~8 with a real save)

### HV.1 -- `migrate` lints by default and writes the report beside the output

Validates: the default-on wiring, the `.lint.json` placement, exit 0 on a clean output.

- [ ] **Steps** (same in every shell; replace `<scratch>` with your scratch folder):
  ```
  ck3-save-migrator migrate <scratch>/old.ck3 --rules all --reference "<reference>" --wos-shape faith -o <scratch>/out.migrated.ck3
  ```
- [ ] **Expected:** the rules' summary, then a `lint` block on stdout listing the four severities with counts; exit code 0; two new files: `<scratch>/out.migrated.ck3` and `<scratch>/out.migrated.lint.json` beside it. (With `--wos-shape both` and a save that has a custom faith, the outputs are `out__wos-faith.migrated.ck3` and `out__wos-rite.migrated.ck3`, each with its own `.lint.json`.) A full migrate of a 200 MB gamestate takes about 3.5 minutes, the lint about 1 minute of that.
- [ ] **Why this matters:** if lint does not run by default, a user loads a save the tool already knew the game would reject.

### HV.2 -- the `lint` command on its own

Validates: the standalone command, the same findings as HV.1.

- [ ] **Steps** (the same `--reference` as HV.1, or the DNA family's target length differs):
  ```
  ck3-save-migrator lint <scratch>/out.migrated.ck3 --reference "<reference>" --json <scratch>/lint.json
  ```
- [ ] **Expected:** the same families and counts as the HV.1 block (same numbers, same order); exit 0; `<scratch>/lint.json` written; takes about a minute on a 200 MB save.
- [ ] **Why this matters:** a user who already has a migrated save needs the report without re-running the migration.

### HV.3 -- the reject counts match the game's own log

Validates: the "what 1.20 will log" prediction against reality. **Manual: needs the game.**

- [ ] **Steps:**
  1. Load the migrated output in the game (`-debug_mode -loadsave=<file>`, as in the Phase 1 checklist, HV.3) until the map shows, then quit.
  2. Open `Documents/Paradox Interactive/Crusader Kings III/logs/error.log`.
  3. Count the lines for two families lint predicted, for example `Unexpected DNA string length` and `Unknown on action`:

  **cmd.exe**: `findstr /c:"Unexpected DNA string length" error.log | find /c /v ""`
  **PowerShell**: `(Select-String -Path error.log -SimpleMatch "Unexpected DNA string length").Count`
  **POSIX**: `grep -c "Unexpected DNA string length" error.log`
- [ ] **Expected:** within 5% of lint's predicted count for each save-read family (DNA, on actions, key references, dynasty templates, invalid title templates). The culture family is reported by name only; its line count is not predicted, and the checklist does not require it to match.
- [ ] **Why this matters:** the reject severity is a promise about the game's behaviour; if the numbers drift, the promise is empty.

### HV.4 -- exit code 4 on an error, output still written

Validates: the one exit code users will script against.

- [ ] **Steps:** a correct migration has no errors by construction, so break a copy of the output by hand: open a copy of the gamestate (see Prerequisites for the unzip), change one character's `rite=<n>` to `rite=999999`, re-zip it as `<scratch>/broken.migrated.ck3` (the Phase 1 checklist's Section 1 has the re-zip two-liner), then:
  ```
  ck3-save-migrator lint <scratch>/broken.migrated.ck3 --reference "<reference>"
  ```
  and print the exit code: **cmd.exe** `echo %ERRORLEVEL%` · **PowerShell** `$LASTEXITCODE` · **POSIX** `echo $?`
- [ ] **Expected:** exit code 4; an `ERROR` line naming the failed check ("character rite ids exist", with the character as an example) in plain words. The `migrate`-time exit 4 with the output still written is covered by the automated test `test_lint_error_exits_4_and_still_writes`; a scripted recipe that makes `migrate` itself produce it on a real save does not exist, because partial rule sets leave the save in the old layout and lint then skips the religion checks with a message (that skip is also worth seeing: run `migrate <scratch>/old.ck3 --rules R1,R7 --reference none -o <scratch>/partial.migrated.ck3` and expect exit 0 plus a `skipped: religion references ... (not a 1.20-layout save)` line).
- [ ] **Why this matters:** a script that treats "exit 0" as "safe to load" must be able to trust it.

### HV.5 -- `--no-lint` and `--dry-run` behave as named

- [ ] **Steps:**
  ```
  ck3-save-migrator migrate <scratch>/old.ck3 --rules all --reference "<reference>" --wos-shape faith --no-lint -o <scratch>/nolint.migrated.ck3
  ck3-save-migrator migrate <scratch>/old.ck3 --rules all --reference "<reference>" --wos-shape faith --dry-run -o <scratch>/dry.migrated.ck3
  ```
- [ ] **Expected:** the first writes the output and no `.lint.json`, and prints no lint block; the second writes nothing at all (no output, no `.lint.json`), and still prints the lint block to stdout.
- [ ] **Why this matters:** `--dry-run` leaving a `.lint.json` behind would make "writes nothing" false.

## Section 1: the report's shape (~5 min; works on the synthetic fixture)

### 1.1 Four severities, readable on a plain terminal

- [ ] **Steps:** read the stdout of HV.1 or HV.2 (a migrated output; the old-layout fixture shows only structure findings). Without a real save: `ck3-save-migrator lint <scratch>/fixture.ck3 --reference none --game-dir none` shows the structure check and the skip lines only.
- [ ] **Expected:** lines prefixed `ERROR`, `WARN`, `REJECT`, `INFO` (only those that have findings); each family with a plain-language description on its first line and the game's raw log text on the second; indented examples; counts formatted with thousands separators; no characters outside ASCII in the labels (Windows cmd.exe at codepage 437 shows them unchanged).
- [ ] **Check:** is each family's description understandable without the design document? Note any that are not.

### 1.2 The JSON file is complete and machine-readable

- [ ] **Steps:** `python -m json.tool <scratch>/lint.json` (from HV.2)
- [ ] **Expected:** a top-level object with the four severity counts (`errors`, `warnings`, `reject`, `info`), one flat `findings` list whose entries carry `check`, `severity`, `count`, `examples` and `note` (the list is flat by design; group by `severity` if you need to), a `skipped` list, and a `stats` block naming the game folder, the reference file and the mod folders actually used, plus the save's listed mods that were not found. No absolute paths to your home folder other than the ones you passed in.

### 1.3 The `--report` file carries the same block

- [ ] **Steps:** rerun HV.1 with `--report <scratch>/report.json`; open it.
- [ ] **Expected:** a `lint` key whose content equals the `.lint.json` beside the output (same counts).

## Section 2: the mods switch (~5 min; needs a real save that lists Workshop mods)

### 2.1 `--lint-mods save` (default) counts the mods' definitions as known

- [ ] **Steps:** HV.1 as run; note the "key references" and "on actions" counts.
- [ ] **Steps:** rerun with `--lint-mods none`.
- [ ] **Expected:** the counts rise with `none` (every mod-defined key is now unknown; on the maintainers' campaign, key references 982 -> 2,985 and on actions 3 -> 3,139 with 28 of 32 listed mods installed); the `stats` block lists the mod folders used in the first run and none in the second, and names the listed mods that were not found, with one stdout line saying so. If none of the save's mods are installed on this machine, both runs give the same numbers.

### 2.2 The `lint` command's `--mods` does the same

- [ ] **Steps:** `ck3-save-migrator lint <output> --mods none --json <scratch>/lint-none.json`
- [ ] **Expected:** same numbers as 2.1's second run.

## Section 3: without the game, without the reference (~3 min)

### 3.1 No reference

- [ ] **Steps:** `ck3-save-migrator lint <output> --reference none`
- [ ] **Expected:** the DNA-length family is skipped with a one-line message saying why; the key-name INFO still runs as long as a game folder or mods are available (it is skipped only when no source at all exists); everything else runs; exit 0.

### 3.2 No game folder

- [ ] **Steps:** `ck3-save-migrator lint <output> --game-dir none`
- [ ] **Expected:** one skip line naming all six families that need `common/` (key references, on actions, dynasty templates, title templates, duplicate titles, cultures); structure, cross-references and DNA still run; exit 0.

### 3.3 Wrong game folder

- [ ] **Steps:** `ck3-save-migrator lint <output> --game-dir <scratch>`
- [ ] **Expected:** a clear refusal or skip naming the folder and what was expected in it (a `common/landed_titles` folder), not a traceback, and **not** a silent fall-through to the Steam install: the output must differ from a run without the flag (compare the `stats` block).

### 3.4 Discovery is off in the test suite

- [ ] **Steps:** `python -m pytest -q`
- [ ] **Expected:** 210 passed, 3 skipped, in well under a minute (around 15 to 20 s). If the suite takes more than a minute, discovery of the real game or reference is leaking in: check that `tests/conftest.py` sets `CK3_GAME_DIR=none` and `CK3_REFERENCE_SAVE=none`.
- [ ] **Steps (opt-in real-save tests):** set `CK3_REAL_SAVES=1` and rerun `python -m pytest -q tests/test_lint.py`; the three skipped tests run (about two minutes; they need the maintainers' archived logs and saves, so outside the project they skip with a message).

## Section 4: a human reads the report (~10 min; needs a real save)

### 4.1 Do the examples help?

- [ ] For each REJECT family, open the first example in the migrated gamestate (the Phase 1 checklist shows how to unzip it) and confirm the example points at a real line of that kind.
- [ ] Judge: would a player who does not know the game's internals understand from the family's description what will happen when they load the save (nothing, a log line, a changed face, a missing culture)? Note the wording you would change.

### 4.2 Does anything that matters go unreported?

- [ ] Compare the game's `error.log` from HV.3 against lint's families. List any message with more than ~50 lines that lint has no family for. (Known and accepted: runtime script errors, including the culture "Failed to fetch" lines; bare `type=` enum values such as `prisoner_of_war`; opinion modifiers, which the game drops silently.)

## What the automated tests DON'T cover

- **Your game's actual log.** The 5% calibration is against two archived logs from one campaign on one machine; HV.3 is the only check against a different save or a different game build.
- **The real game folder.** 1,736 of 2,077 `common/` files start with a byte-order mark; the tests use a synthetic folder plus one BOM fixture. Section 3's skips and Section 2's mod folders need a real install.
- **Readability.** Whether the family descriptions and the examples mean anything to a player (Section 4).
- **Terminal rendering** on Windows codepage 437/1252 and narrow terminals (1.1).
- **Timing feel.** About a minute per lint on a 200 MB save, about 20 s of it loading game data; whether that is acceptable inside every `migrate` is a judgement.
- **Mods not installed locally.** The tests fake mod folders; the message when a listed mod is absent is only seen for real (2.1).

## Reporting issues found

1. Note the section and step number and your shell.
2. Capture the exact command, stdout, exit code, and the `.lint.json`.
3. For a count mismatch (HV.3), attach the relevant `error.log` lines and the save's game version from `ck3-save-migrator inspect`.
4. File an issue referencing this checklist and the version.

## Cleanup

Delete the scratch folder:

**cmd.exe**: `rmdir /s /q %CK3_SCRATCH%` · **PowerShell**: `Remove-Item -Recurse -Force $env:CK3_SCRATCH` · **POSIX**: `rm -rf "$CK3_SCRATCH"`

Unset the variables: **cmd.exe** `set CK3_SCRATCH=` and `set CK3_REFERENCE_SAVE=` · **PowerShell** `Remove-Item Env:\CK3_SCRATCH, Env:\CK3_REFERENCE_SAVE` · **POSIX** `unset CK3_SCRATCH CK3_REFERENCE_SAVE`.

Nothing in the game's folders was changed by this checklist. If you loaded a save for HV.3, the game may have written an autosave to its own `save games` folder; it is yours to keep or delete.
