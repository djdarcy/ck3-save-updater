# Human Test Checklist: Phase 1 -- load-and-repair migration CLI (1.8-era save into CK3 1.20)

**Target version:** 0.2.0
**Ships with commit:** TBD (first working release: `inspect`, `migrate`, `rules`; rules R1-R12)
**Companion automated tests:** 151 collected -- tests/test_savefile.py (42), tests/test_gamestate.py (43), tests/test_rules.py (30), tests/test_religion.py (29), tests/test_version.py (7)

## What this is

The checklist a person walks to confirm that `ck3-save-migrator` does what the automated suite cannot prove: that a real 30 MB save written by Crusader Kings III 1.8.1 goes through `migrate` and **loads in the installed game (1.20.x)**, that the two custom-faith shapes both load, that outputs never touch the input, and that the tool behaves on a Windows console with real paths. It is written for the maintainer and for anyone with an old save and a current install. Game launches are the point of the exercise and are **manual**; everything else can be scripted.

## Prerequisites

1. **Python 3.10+** and the package installed editable: `pip install -e ".[dev]"` from the repo root. `ck3-save-migrator --version` prints `ck3-save-migrator 0.2.0`.
2. **Crusader Kings III 1.20.x** installed (Steam). Note its `game` folder, e.g. `E:\SteamLibrary\steamapps\common\Crusader Kings III\game`.
3. **An old save** written by CK3 1.8.x (or any pre-1.20 version), plain-text kind (a manual save, not an autosave: autosaves are binary and are refused with a clear message). Call it `OLD.ck3` below. Copy it; never point the tool at the only copy.
4. **A reference save** written by the installed game: start any game, `Esc > Save Game`, name it `ref.ck3`, quit. (The debug console's `save_text` is developer-only; the menu works.) For a 987-era campaign the maintainers use a reference started on the same date via a local bookmark mod; any date works for this checklist.
5. **A scratch folder** for every output, e.g. `%TEMP%\ck3mig` -- nothing in this checklist writes into `Documents\Paradox Interactive\Crusader Kings III` except the one file you copy there by hand in Section 4.
6. **State isolation**: the tool reads `CK3_GAME_DIR` and `CK3_REFERENCE_SAVE`; set them for the session so no command needs the long paths:

   **cmd.exe**:
   ```cmd
   set CK3_GAME_DIR=E:\SteamLibrary\steamapps\common\Crusader Kings III\game
   set CK3_REFERENCE_SAVE=%TEMP%\ck3mig\ref.ck3
   mkdir %TEMP%\ck3mig
   ```
   **PowerShell**:
   ```powershell
   $env:CK3_GAME_DIR = "E:\SteamLibrary\steamapps\common\Crusader Kings III\game"
   $env:CK3_REFERENCE_SAVE = "$env:TEMP\ck3mig\ref.ck3"
   New-Item -ItemType Directory -Force "$env:TEMP\ck3mig" | Out-Null
   ```
   **POSIX**:
   ```bash
   export CK3_GAME_DIR="$HOME/.steam/steam/steamapps/common/Crusader Kings III/game"
   export CK3_REFERENCE_SAVE=/tmp/ck3mig/ref.ck3
   mkdir -p /tmp/ck3mig
   ```
7. **Reset between sections**: delete the scratch folder's `*.migrated.ck3` and `*.json` files; the inputs are never modified, so nothing else needs resetting. Hash `OLD.ck3` once before you start and compare at the end (Cleanup).

## High-Value Verification (~5 minutes, plus one 1-minute game launch)

**If you only have 5 minutes**, run these six. They are the "did the work ship" tests.

### HV.1 -- `inspect` reads a real old save

Validates: header parsing (kind, meta length, newline), zip member discovery, the decompressed size.

- [ ] **Steps** (same across shells):
  ```
  ck3-save-migrator inspect OLD.ck3
  ```
- [ ] **Expected:** four lines: `file`, `header SAV01 02 ...  (kind 02 UnifiedText, meta length N, newline LF|CRLF)`, `meta block N bytes`, `member gamestate <bytes> bytes inflated`. Exit code 0. For a binary autosave: a one-line refusal naming kind 03 and exit code 1.
- [ ] **Why this matters:** every later step trusts this parse; a wrong meta length corrupts every output.

### HV.2 -- a no-op `migrate` of the reference save loads in the game

Validates: the writer (re-deflate, derived meta block, recomputed length) produces a file the game accepts.

- [ ] **Steps**:
  ```
  ck3-save-migrator migrate ref.ck3 --recompress -o %TEMP%\ck3mig\ref.roundtrip.ck3
  ck3-save-migrator inspect %TEMP%\ck3mig\ref.roundtrip.ck3
  ```
  (PowerShell/POSIX: substitute `$env:TEMP` / `/tmp`.) Copy `ref.roundtrip.ck3` into the game's `save games` folder, start the game, Load Game, pick it.
- [ ] **Expected:** `inspect` reports the same inflated size as the original; the game loads it to the map. Exit code 0.
- [ ] **Why this matters:** if the format layer is wrong, nothing else can be tested.

### HV.3 -- `migrate --rules all` on the old save writes two outputs and a report

Validates: the whole rule chain on a real 222 MB gamestate, both custom-faith shapes.

- [ ] **Steps**:
  ```
  ck3-save-migrator migrate OLD.ck3 --rules all --reference ref.ck3 --wos-shape both -o %TEMP%\ck3mig\old.migrated.ck3 --report %TEMP%\ck3mig\old.report.json
  ```
- [ ] **Expected:** two files, `old__wos-faith.migrated.ck3` and `old__wos-rite.migrated.ck3`, and two reports named the same way (`old__wos-faith.report.json`, `old__wos-rite.report.json` -- the `--report` path is suffixed per shape); the console prints each rule's matched/edited counts; exit 0; wall time ~3-5 minutes on a 222 MB gamestate (the religion rules are the slow part; longer under CPU contention). If the save has no custom faith, one output and one report (unsuffixed).
- [ ] **Why this matters:** this is the product.

### HV.4 -- the migrated save loads in the installed game (manual)

Validates: acceptance checks A3 and A6 of the design: the game reaches the map with the migrated file.

- [ ] **Steps:** copy `old__wos-faith.migrated.ck3` into `Documents\Paradox Interactive\Crusader Kings III\save games` as `MIGRATE_TEST__old_faith.ck3`; start the game with **no mods** enabled; Load Game; pick it.
- [ ] **Expected:** the loading screen completes and the map appears, paused, on the save's date, with the player's character, titles and treasury. The in-game error log (`Documents\...\logs\error.log`) contains **no** lines matching `Failed to fetch a valid faith`, `rite trigger`, `scope:faith.religion`, `is_holy_site_of`. Remaining lines are expected and documented: `Unexpected DNA string length` (portraits), `Failed to fetch a valid culture '...'`, VIET/other mod on_actions when the save had mods.
- [ ] **Why this matters:** "loads" is the only judge that counts; the suite cannot run the game.

### HV.5 -- the report explains what changed and what was lost

Validates: the JSON report's contract (rule rows with counts, `lost` typed entries, `assumptions`, `check`).

- [ ] **Steps**:
  ```
  python -m json.tool %TEMP%\ck3mig\old__wos-faith.report.json | more
  ```
- [ ] **Expected:** `input_sha256` equals your pre-run hash of `OLD.ck3`; one row per rule with `matched`/`edited`; R8's `extra.lost` lists typed entries (holy-site baronies missing from the new map, etc.); R12's `check` shows `without_rite: 0` and `dangling_rite_ids: 0`; `assumptions` names the house-head inheritance rule.
- [ ] **Why this matters:** a migration that cannot say what it dropped is not trustworthy.

### HV.6 -- outputs never clobber inputs

Validates: the write guards.

- [ ] **Steps**:
  ```
  ck3-save-migrator migrate OLD.ck3 -o OLD.ck3
  ck3-save-migrator migrate OLD.ck3 --rules all -o %TEMP%\ck3mig\old.migrated.ck3
  ```
  (second command run twice)
- [ ] **Expected:** the first refuses ("in place") with exit code 2 even with `--force`; the second succeeds once, then refuses because the output exists (exit 2) **before doing any work** until `--force` is given. `OLD.ck3`'s hash is unchanged. A missing output directory is refused with a plain message naming the directory (exit 1), no traceback.
- [ ] **Why this matters:** the user's only copy of a campaign must be safe by construction.

## Section 1: `inspect` (~2 min)

### 1.1 Old save, reference save, migrated save
- [ ] **Steps:** `inspect` each of `OLD.ck3`, `ref.ck3`, `old__wos-faith.migrated.ck3`.
- [ ] **Expected:** kind 02 for all three; the migrated file's meta length differs from the original's by the blank game-rule slots removed (3 bytes per slot) offset by the longer version strings the bump writes (on the maintainers' save: -207 + 4 = -203 bytes); `inspect` prints no warning. The reference's `save_game_version` (visible in the meta block if you open the file in a text editor) is 18 for 1.20.x.

### 1.2 A file that is not a save
- [ ] **Steps:** `ck3-save-migrator inspect README.md`
- [ ] **Expected:** one clear error line (not a traceback), exit code 1.

## Section 2: `migrate` outputs and the report (~5 min)

### 2.1 Dry run writes nothing
- [ ] **Steps:** `ck3-save-migrator migrate OLD.ck3 --rules all --dry-run --report %TEMP%\ck3mig\dry.json`
- [ ] **Expected:** the counts print, the report is written, **no** `.ck3` appears in the scratch folder, exit 0.

### 2.2 Subtractive rules only, no reference
- [ ] **Steps:** `ck3-save-migrator migrate OLD.ck3 --rules R1,R2,R3,R4,R5,R7 -o %TEMP%\ck3mig\subtractive.ck3 --report %TEMP%\ck3mig\subtractive.json`
- [ ] **Expected:** one output (no faith shapes without R10), report rows only for the rules named, `version` in the meta block is the target version and `save_game_version=18`.
- [ ] **Check (manual, optional):** this file loads in the game too (it did for the maintainers' 987 save) -- but with the religion layer empty, so expect many `faith`/`rite` errors in the log; that is the state R8-R12 fix.

### 2.3 `--reference none` disables the religion rules
- [ ] **Steps:** `ck3-save-migrator migrate OLD.ck3 --rules all --reference none --dry-run`
- [ ] **Expected:** R8-R12 are reported as skipped (no reference), the rest run, exit 0.

### 2.4 The `rules` listing matches the report
- [ ] **Steps:** `ck3-save-migrator rules`
- [ ] **Expected:** twelve rows in registry order (R1-R6, R11, R8, R10, R9, R12, R7), each with a `since` and a one-line description; the ids match the report's rows.

### 2.5 Portraits version flag
- [ ] **Steps:** `ck3-save-migrator migrate OLD.ck3 --rules R7 --portraits-version 5 --dry-run --report %TEMP%\ck3mig\pv.json`
- [ ] **Expected:** R7 reports 3 edits (version, save_game_version, portraits_version). Note for testers: the maintainers leave portraits_version alone by default because the DNA layout changed and the game regenerates faces either way.

## Section 3: the game launches (manual, ~10 min)

Use **no mods** for all of these unless a step says otherwise. Keep the Documents folder clean: only `MIGRATE_TEST__*` files go in, and they come out in Cleanup.

### 3.1 Both custom-faith shapes load
- [ ] **Steps:** load `MIGRATE_TEST__old_faith.ck3` (HV.4), quit; copy `old__wos-rite.migrated.ck3` as `MIGRATE_TEST__old_rite.ck3`, load it, quit.
- [ ] **Expected:** both reach the map. In the faith window (click the faith icon), the faith shape shows the custom faith as its own faith with its own head; the rite shape shows it as a rite of the parent faith.

### 3.2 Catholicism and Orthodoxy keep their heads
- [ ] **Steps:** in the loaded game, open the faith window for Catholic (search a Catholic character, click their faith).
- [ ] **Expected:** the Pope is listed as head; Orthodox shows the Patriarch; neither is merged into the custom faith.

### 3.3 Time passes
- [ ] **Steps:** unpause at speed 3; let 3 in-game months run; pause.
- [ ] **Expected:** no crash; no wave of deaths (watch the notifications); the court and council portraits fill in. Known at 0.2.0: regions added to the map after the save's version are **not yet populated** and may show as the player's -- that is the next phase's work, not a failure of this one.

### 3.4 Lineage of the custom faith (expected NOT visible)
- [ ] **Steps:** hover the fervor value in the custom faith's window.
- [ ] **Expected:** the 1.20 faith window does not display a faith's origin or its history, by the maintainers' reading of `gui/window_faith.gui`. If you *do* see "origin: Insular Celtic" or dated history entries, note it -- it is good news and a finding.

### 3.5 Unmodified old save, for contrast (optional, ~1 min)
- [ ] **Steps:** copy `OLD.ck3` as `MIGRATE_TEST__orig.ck3`, load it.
- [ ] **Expected:** the game reads it and **crashes shortly after** "Setup powerful vassals" (an access violation), leaving a crash folder under `Documents\...\crashes\`. This is the baseline the tool exists to fix; if it loads, your save is newer than the tool assumes -- say so in a report.

## Section 4: Windows and console behaviour (~3 min)

### 4.1 Paths with spaces and non-ASCII names
- [ ] **Steps:** copy `OLD.ck3` to a folder with a space and an accented character in the path; run HV.3 against it from cmd.exe.
- [ ] **Expected:** works; the report's `input` path is correct; no `UnicodeEncodeError` on the console (the tool reconfigures stdout to UTF-8 with replacement).

### 4.2 Console encoding
- [ ] **Steps:** in cmd.exe with the default codepage (`chcp` shows 437 or 1252), run `ck3-save-migrator rules` and `inspect`.
- [ ] **Expected:** readable ASCII output; no mojibake, no crash.

### 4.3 Large file timing feel
- [ ] **Steps:** time HV.3 on a 200+ MB gamestate.
- [ ] **Expected:** subtractive rules in under a minute; the religion rules a few minutes; memory stays under ~2 GB. If a rule takes more than 10 minutes, that is a regression (the 0.2.0 fix for a re-tokenising hot loop is the reference).

## What the automated tests DON'T cover

- Whether the game loads the output (HV.2, HV.4, Section 3) -- no test can run CK3.
- Behaviour on a real 222 MB gamestate end to end (the real-save tests are opt-in, `CK3_REAL_SAVES=1`, and skipped in CI).
- The two faith shapes as *gameplay*: which one feels right is a human judgment (3.1).
- Windows console codepages, paths with spaces/accents, timing feel (Section 4).
- The game's own tolerance: which leftover errors (DNA, cultures) matter in play (3.3).
- Interaction with mods: 0.2.0 runs mods-off; a save that depended on mods loads with their keys missing.

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command, its output, and the game's `error.log` tail if a launch was involved.
3. Keep the report JSON next to the output.
4. File an issue on `djdarcy/ck3-save-migrator` referencing this checklist (`v0.2.0__Phase1`) and the version.
