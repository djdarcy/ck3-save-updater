## What this is

Version 0.4.0 gathers the work of 0.3.1 to 0.3.4 into the release that makes an old campaign playable in the current game. It adds the opt-in new-map rules (`--rules all,R15,R14,R16`), which bring in the regions 1.20 added from a 1.20 save at the campaign's date, rename or remove the titles 1.20 removed or moved, and settle the counties 1.20 redrew around the campaign's baronies, listing every change in the report. It makes the command line safer: a rule chosen without the rules it needs is refused before the save is read, `migrate` with no `--rules` runs the full migration, a run that would change nothing writes nothing, `--force` never overwrites the input under any name, and `--bump-version` is deprecated. `lint` gains four checks (county records, registered template cultures, rite numbers without a rites database, numbers sharing a slot). This checklist is for anyone with Python and this repository: every step outside the marked real-save section runs on small synthetic saves built from the project's test fixtures. The automated tests prove the rules on those fixtures in memory; this checklist checks what only a person at a shell can see: the files on disk, the messages, the refusals and the exit codes.

## Prerequisites

1. Windows, macOS or Linux with Python 3.10+ and this repository checked out; `pip install -e ".[dev]"` done. `ck3-save-migrator --version` prints the version under test.
2. No game install and no real save are needed outside the "Real-save verification" section.
3. **Isolation:** every file goes to a scratch folder. Nothing in this checklist writes to the game's folders.
4. **Turn discovery off**, so a game install or a reference save on your machine does not change what the synthetic runs print: set `CK3_GAME_DIR` and `CK3_REFERENCE_SAVE` to `none` for the session. The Expected text below was recorded that way.

Set the scratch folder and the two variables (pick your shell):

**cmd.exe**:
```cmd
set CK3_SCRATCH=%TEMP%\ck3-040-check
mkdir %CK3_SCRATCH%
set CK3_GAME_DIR=none
set CK3_REFERENCE_SAVE=none
```

**PowerShell**:
```powershell
$env:CK3_SCRATCH = "$env:TEMP\ck3-040-check"
New-Item -ItemType Directory -Force $env:CK3_SCRATCH | Out-Null
$env:CK3_GAME_DIR = "none"
$env:CK3_REFERENCE_SAVE = "none"
```

**POSIX**:
```bash
export CK3_SCRATCH=/tmp/ck3-040-check
mkdir -p "$CK3_SCRATCH"
export CK3_GAME_DIR=none
export CK3_REFERENCE_SAVE=none
```

### Building the synthetic saves

Run these three from the **repository's root folder** (they import the test fixtures). Each reads the scratch folder from `CK3_SCRATCH`, so each command is the same in every shell.

**B.1 -- an old campaign and a 1.20 reference** (`My_Old_Campaign.ck3`, a tiny 1.8.1 save with a custom faith; `A_New_1_20_Game.ck3`, a tiny 1.20 save that has two titles the old one lacks, `b_samarkand` and `d_cd_ostia`):
```
python -c "import os; from tests.fixtures.make_ck3 import build_ck3; from tests.fixtures.religion import OLD_META, OLD_BODY, REF_META, REF_BODY; d = os.environ['CK3_SCRATCH']; open(os.path.join(d, 'My_Old_Campaign.ck3'), 'wb').write(build_ck3(meta=OLD_META, body=OLD_BODY)); open(os.path.join(d, 'A_New_1_20_Game.ck3'), 'wb').write(build_ck3(meta=REF_META, body=REF_BODY))"
```

**B.2 -- two tiny game maps** for R15 (`Old_Game` and `New_Game`, each holding only `common/landed_titles`; the only difference is that the old map's `c_test` is called `c_holy_city` in the new one, which also has the reference's two extra titles):
```
python -c "import os, pathlib; d = pathlib.Path(os.environ['CK3_SCRATCH']); old = 'k_papal_state = { } d_celtic_seat = { } d_sunni = { c_test = { b_jerusalem = { province = 1 } } }'; new = old.replace('c_test', 'c_holy_city') + ' b_samarkand = { province = 2 } d_cd_ostia = { }'; [((d / k / 'common' / 'landed_titles').mkdir(parents=True, exist_ok=True), (d / k / 'common' / 'landed_titles' / '00_landed_titles.txt').write_text(v + chr(10))) for k, v in (('Old_Game', old), ('New_Game', new))]"
```

**B.3 -- a broken save** (`Broken.ck3`) carrying one of each defect the new lint checks look for: two characters numbered 5 and 16777221 (the same slot under two generations), a held county `c_a` with no county record, characters with rite numbers but no rites database, and a culture made from the `han` template missing from the list of template cultures:
```
python -c "import os; from tests.fixtures.make_ck3 import build_ck3, DEFAULT_META; body = b'living={\n1={\n\trite=7\n}\n5={\n\trite=7\n}\n}\ncharacters={\n\tdead_prunable={\n16777221={\n}\n\t}\n}\nlanded_titles={\n\tlanded_titles={\n0={\n\tkey=c_a\n\tholder=1\n}\n\t}\n}\ncounty_manager={\n\tcounties={\n\t}\n}\nculture_manager={\n\ttemplate_cultures={ 0 }\n\tcultures={\n0={\n\t\t\tculture_template=irish\n}\n1={\n\t\t\tculture_template=han\n}\n\t}\n}\n'; open(os.path.join(os.environ['CK3_SCRATCH'], 'Broken.ck3'), 'wb').write(build_ck3(meta=DEFAULT_META, body=body))"
```

Then go to the scratch folder; every step below runs there and uses the file names directly:

**cmd.exe**: `cd /d %CK3_SCRATCH%` · **PowerShell**: `Set-Location $env:CK3_SCRATCH` · **POSIX**: `cd "$CK3_SCRATCH"`

Printing the exit code of the last command (used throughout):

**cmd.exe**: `echo %ERRORLEVEL%` · **PowerShell**: `$LASTEXITCODE` · **POSIX**: `echo $?`

Listing the scratch folder:

**cmd.exe**: `dir /b` · **PowerShell**: `Get-ChildItem -Name` · **POSIX**: `ls`

**Reset between sections:** delete the outputs, keeping the three inputs and the two map folders:

**cmd.exe**: `del /q *.migrated.ck3 *.json Second_Name.ck3 2>nul` · **PowerShell**: `Remove-Item *.migrated.ck3, *.json, Second_Name.ck3 -ErrorAction SilentlyContinue` · **POSIX**: `rm -f *.migrated.ck3 *.json Second_Name.ck3`

The `sha256` values printed by `migrate` depend on your Python's compression library and may differ from the ones a maintainer records; nothing below asks you to compare them.

### HV.1 -- the new-map rules run, list every change, and a second run writes nothing

Validates: `--rules all,R15,R14,R16` end to end through the command line, the report rows, idempotence.

- [ ] **Steps** (same in every shell):
  ```

  python -c "import json; r = json.load(open('Transplanted.report.json')); print(json.dumps([e for e in r['rules'] if e['id'] == 'R15'][0]['extra']['table'], indent=1))"
  ck3-save-migrator migrate Transplanted.migrated.ck3 --rules all,R15,R14,R16 --reference A_New_1_20_Game.ck3 --old-game-dir Old_Game --game-dir New_Game --wos-shape faith -o Again.migrated.ck3
  ```
- [ ] **Expected (first command):** exit 0; `wrote: Transplanted.migrated.ck3`; `rules applied : 16  (wos shape: faith)`; the rule lines include `R15 dead-titles  matched 1  edited 2`, `R14 new-titles  matched 1  edited 0`, `R16 people  matched 0  edited 0` and `R17 transplant-write  matched 2  edited 2` (R17 was not named on the command line; it came along by itself). The lint block reads `lint          : 0 error(s), 0 warning(s), 1 family(ies) 1.20 will log, 1 info`: the tiny game folder does not define two names the fixture uses (`real_modifier`, `artifact_monthly_prestige`), so they appear under `Failed to read key reference`. Three new files: `Transplanted.migrated.ck3`, `Transplanted.migrated.lint.json`, `Transplanted.report.json`.
- [ ] **Expected (second command):** one row for `c_test`: `"class": "clean"`, `"successors": ["c_holy_city"]`, `"outcome": "kept by the campaign's holder as c_holy_city"`.

- [ ] **Why this matters:** the new-map rules are the release's headline; a report that leaves out a change, or a re-run that undoes part of the first migration (the bug fixed in 0.3.4), costs a player their campaign.

### HV.3 -- `--force` never overwrites the input, also under a second name

Validates: the output-is-the-input refusal survives `--force`, including a hard link.

- [ ] **Steps:** note the input's hash (same in every shell):
  ```
  python -c "import hashlib, sys; print(hashlib.sha256(open(sys.argv[1], 'rb').read()).hexdigest())" My_Old_Campaign.ck3
  ck3-save-migrator migrate My_Old_Campaign.ck3 --reference A_New_1_20_Game.ck3 --wos-shape faith -o My_Old_Campaign.ck3 --force
  ```
  Print the exit code. Then make a second name for the input (a hard link):

  **cmd.exe**: `mklink /H Second_Name.ck3 My_Old_Campaign.ck3` · **PowerShell**: `New-Item -ItemType HardLink -Path Second_Name.ck3 -Target My_Old_Campaign.ck3` · **POSIX**: `ln My_Old_Campaign.ck3 Second_Name.ck3`

  ```
  ck3-save-migrator migrate My_Old_Campaign.ck3 --reference A_New_1_20_Game.ck3 --wos-shape faith -o Second_Name.ck3 --force
  ```
  Print the exit code, then hash `My_Old_Campaign.ck3` again with the first command.
- [ ] **Expected:** `ERROR: refusing to write over the input file: My_Old_Campaign.ck3`, exit 2; then `ERROR: refusing to write over the input file: Second_Name.ck3`, exit 2; the two hashes are equal.
- [ ] **Why this matters:** the input is the player's only copy of their campaign; "the input file is never modified" has to hold however the output is named.

## What the automated tests DON'T cover

- **The game itself.** Whether the output loads, plays, and survives the game's own re-save (the marked section).
- **A real map rework.** The synthetic maps differ by one county; the real one by thousands of titles and provinces. R15's classes other than "clean" and "dropped" (split, wasteland, matched by key, moved baronies) and the settlement of redrawn counties are tested only in memory.
- **Two messages no test reads.** The lint check "held counties have a county record" has no test of its own (the transplant tests check that county records are carried, not that lint reports a missing one), and the `--bump-version` test checks that the version is still bumped, not the deprecation warning. HV.4 and 1.6 are where these are seen.
- **The shell.** Hard links made by the operating system, exit codes as each shell reports them, file names as each shell passes them (HV.3, HV.4).
- **Timing on a large save** and how the `-v` summaries read on a real transplant of thousands of titles.
- **Readability.** Whether the refusals and the report's outcome sentences tell a player what to do next.

## Reporting issues found

1. Note the section and step number and your shell.
2. Capture the exact command, the output, the exit code, and any `.json` file the step wrote.
3. For a synthetic step, say whether you set `CK3_GAME_DIR` and `CK3_REFERENCE_SAVE` to `none`.
4. File an issue referencing this checklist and the version.
