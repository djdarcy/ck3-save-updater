# Human Test Checklist: the carried-fields check (lint and update)

**Target version:** 0.5.21
**Ships with commit:** v0.5.21: lint names the fields an update left out (TBD hash)
**Companion automated tests:** 12 in `tests/test_lint_fields.py`; 14 in `tests/test_field_baseline.py` (0.5.20); 10 field-coverage tests in `tests/test_savediff_keys.py` (0.5.19); mutation reports in `tests/mutation/`.

## What this is

From 0.5.21, `lint` and the check `update` runs on what it writes report entries that lack a field the game's own entries of that kind carry, or leave it empty. The automated tests prove the logic on small synthetic saves. This checklist is for a person with real saves: whether the lines are right on the game's own save and on updated campaigns, whether a player can read them, and whether the extra minute is acceptable.

## Prerequisites

1. ck3-save-updater 0.5.21 installed (`pip install -e .` in a checkout, or the release), and Python on the path.
2. Four saves, each **copied** to a scratch folder first (lint only reads, but keep originals untouched anyway):
   - **A** a save the game itself wrote in 1.20.1.2 (a new game, saved once, is best);
   - **B** a save updated by ck3update **before 0.5.18** that has a custom faith (any update output from 0.5.0 to 0.5.17);
   - **C** the same campaign updated with 0.5.18 or later;
   - **D** an old save that was never updated (1.8.x or similar).
3. Nothing in this checklist writes outside your scratch folder. No game launch is needed.

Commands below are the same in cmd.exe, PowerShell and POSIX shells except where a block is labelled; quote paths with spaces.

## High-Value Verification (~5 minutes, plus about a minute per large save)

### HV.1 -- The game's own save is clean

Validates: the check does not cry wolf on the game's own data (the tolerance for fields the game itself leaves out of some entries).

- [ ] **Steps:** `python -m ck3_save_migrator lint "<A>"`
- [ ] **Expected:** no line headed "entries carry the fields the game's own entries carry". An info line "fields left out on purpose or filled by the game" may list `rites/database ... rite_type` with its reason.
- [ ] **Why this matters:** if the game's own save is flagged, every player's report is noise and the real gaps drown.

### HV.2 -- The F25 faith is named, with what it costs

Validates: the bug that started this work is caught, in a player's words.

- [ ] **Steps:** `python -m ck3_save_migrator lint "<B>"`
- [ ] **Expected:** under "entries carry the fields...", a line `faiths/database: 1 of N lack `faith_type` ... e.g. <the custom faith's id> ... -- event text that names the faith's god shows a blank`.
- [ ] **Why this matters:** this is exactly the blank god name a player saw in "A Poetic Friendship"; the tool must find it before the player does.

### HV.3 -- Fixed in 0.5.18, and the line goes away

- [ ] **Steps:** `python -m ck3_save_migrator lint "<C>"`
- [ ] **Expected:** no `faith_type` line. Other lines may remain (eminent holy sites, artifacts, cultures...): those are the gaps still open.
- [ ] **Why this matters:** a check that cannot tell fixed from broken is no use as a gate.

### HV.4 -- No record for the version: skipped, and it says so

- [ ] **Steps:** `python -m ck3_save_migrator lint "<D>"`
- [ ] **Expected:** a line `skipped: carried fields: no field baseline for <version> ships with the tool; pass --reference with a save that version wrote to check them`; no field warnings.
- [ ] **Why this matters:** silence would read as "clean".

### HV.5 -- Update shows the same

- [ ] **Steps:** run your usual `ck3update update "<old save>" ... -o "<scratch>/MIGRATE_TEST__fields.ck3"` (any update you normally run, output in scratch).
- [ ] **Expected:** the output check prints the same kind of lines as `lint` on that output.
- [ ] **Why this matters:** most players never run `lint` by hand; `update` is where they will see it.

## Section 1: Reading the report

### 1.1 The warning lines read as English

- [ ] **Steps:** look at the field lines from HV.2 and HV.3.
- [ ] **Expected:** each says the kind of entry, the field, how many lack it, how many are empty, a few example ids, and how often the game's own entries carry it. Judge: would a player know what to look for, or what to ask about?
- [ ] **Check:** the backticks around field names display correctly in your console (Windows cmd.exe with its default code page included).

### 1.2 The information lines

- [ ] **Expected:** "fields left out on purpose or filled by the game" gives a reason for each (rite type of rites made in play; ethnicity filled on load, with counts). "kinds of entry with nothing to compare with" lists kinds such as `units`, `schemes/active`, and says they were not checked, not that they are clean.

## Section 2: The witness

### 2.1 A reference save replaces the shipped record

- [ ] **Steps:** `python -m ck3_save_migrator lint "<C>" --reference "<A>"`
- [ ] **Expected:** the gloss of the field warning says "compared with the reference save"; the findings are close to HV.3's (the record was made from a save like A).

### 2.2 A save from another start date (if you have one)

- [ ] **Steps:** lint a 1.20.1.2 save the game wrote at another bookmark (867 or 1066).
- [ ] **Expected:** no field warnings, as in HV.1. If some appear, note them: the shipped record came from one start date (987.10.27), and this is the case that would show it.

## Section 3: Cost

### 3.1 The time on a large save

- [ ] **Steps** (pick your shell):

  **cmd.exe**:
  ```cmd
  echo %time% & python -m ck3_save_migrator lint "<C>" > NUL & echo %time%
  ```

  **PowerShell**:
  ```powershell
  Measure-Command { python -m ck3_save_migrator lint "<C>" | Out-Null }
  ```

  **POSIX**:
  ```bash
  time python -m ck3_save_migrator lint "<C>" > /dev/null
  ```
- [ ] **Expected:** about a minute more than 0.5.20's lint on the same save. Judge whether that is acceptable inside `update`.

## What the automated tests DO cover

| Area | Test file | Count |
|---|---|---|
| field reading: same-line keys, empty values, double writings, unkeyed records | `tests/test_savediff_keys.py` | 10 |
| the baseline: structure only, deterministic, version keyed, rounding | `tests/test_field_baseline.py` | 14 |
| the check: F25 named with its cost, empty values, the game against itself, the allowance, allow-list, witness choice, skip note, nothing to compare with, the `fields` switch | `tests/test_lint_fields.py` | 12 |

## What the automated tests DON'T cover

- Real saves of a player's size, and the time the check takes on them.
- Whether the wording helps a player who has never seen the save format.
- Console rendering of the backticks and long lines on Windows code pages.
- Saves from start dates other than 987, and from game versions other than 1.20.1.2.
- Saves with mods that add their own fields.

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command and the lines printed.
3. Keep the save copy that produced them.
4. File an issue referencing this checklist and version 0.5.21.

## Cleanup

Delete the scratch folder's save copies and any `MIGRATE_TEST__fields.ck3` you wrote (recoverable deletes preferred). Nothing else was written.
